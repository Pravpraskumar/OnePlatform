User access mechanism

Who can enter, where, and why.

Designer Platform does not grant application access with one role. Access is the result of identity, tenant membership, product licensing, optional team and project restrictions, screen grants, and an available concurrent session.

Effective access Authenticated user + active organisation membership + active product allocation + eligible team / project + role and menu grant + available session seat

Animated control flow

Access from setup to revocation

1

Create identity

Global Administrator creates a local user, or B2C provisions/links the user at first sign-in.

2

Add membership

Add the user to the organisation as Owner, Admin, or Member and keep the membership active.

3

Assign product

License the product to the organisation with active status, seats, and an optional expiry date.

4

Narrow eligibility

Optionally bind the module to a team. No team means all active organisation members are eligible.

5

Assign role

Give the user a product capability such as CreditGuard Requestor or Reviewer.

6

Grant screens

Map roles to menus as readonly or editable. Product menus also require an active organisation allocation.

7

Allocate project

If the module uses projects, allocate seats to a project and assign the user to that project.

Configuration is cumulative. A role by itself does not create tenant or licensed-product access.

1

Authenticate

Local JWT or Azure AD B2C token establishes the platform identity.

2

Select tenant

The active organisation drives menus, products, projects, and all tenant-scoped calls.

3

Resolve menus

Core merges role grants, upgrades editable over readonly, and removes unlicensed product screens.

4

Resolve project

A project is mandatory when the organisation module has project allocations.

5

Open lease

Core locks the module allocation, verifies eligibility, counts active sessions, and reserves a seat.

6

Authorize API

Backend guards verify identity, organisation authority, resource ownership, and workflow rules.

7

Keep alive

The SPA heartbeats every 30 seconds. Final unmount releases the lease; the reaper closes idle leases.

The browser improves navigation, but the server must independently reject unauthorized calls.

1

Change control

Suspend the user or membership, remove a role, team member, project assignment, or product allocation.

2

Menus recalculate

The next menu request removes screens no longer granted or licensed.

3

Heartbeat checks

Active membership, product allocation, team membership, and project access are checked again.

4

Lease closes

If access is revoked, the session receives an end time and the heartbeat fails.

5

API denies

Tenant and workflow checks continue to block direct calls regardless of stale browser state.

6

Seat returns

Closed or timed-out sessions stop counting against the concurrent allocation.

7

Audit outcome

Administrators verify effective access and running sessions after the change.

Revocation is enforced at runtime; it does not depend only on hiding a navigation item.

A role describes platform or product behavior. Product-linked roles are assigned to the user and contribute menu grants.

Organisation context

  • Admin
  • Member
  • Optional team membership
  • Optional project membership

Product allocation

An organisation module connects a tenant to a product and controls availability, team restriction, dates, and concurrent seats.

Administrator procedures

Common access scenarios

  1. Create or provision the userCreate the identity under Global Administration, or allow B2C just-in-time provisioning. Keep the user active.
  2. Add the user to the organisationChoose Owner, Admin, or Member. Membership is separate from product role assignment.
  3. Confirm the organisation has the appUnder Licenses, assign the product with active status, enough seats, and the intended expiry.
  4. Add team and project eligibilityIf restrictions exist, add the user to the module team and assign the member to each required project.
  5. Assign the product roleAssign Requestor, Reviewer, or both. Menu grants come from the role configuration.
  6. Verify effective accessCheck user settings/effective access, then open the product and confirm a lease can be acquired.
Order matters

A role can be assigned before tenant setup, but the user still cannot consume the product until organisation, team/project, and license gates are satisfied.

  1. Confirm active organisation membershipThe reviewer must belong to the same organisation as the request.
  2. Confirm module eligibilityIf CreditGuard is bound to a team, add the reviewer to that exact team.
  3. Assign CreditGuard ReviewerThe role is assigned in global user administration and is linked to the CreditGuard product.
  4. Verify the reviewer listThe reviewer endpoint intersects membership, module allocation, team eligibility, and Reviewer role.
  5. Preserve current-reviewer authorityOnly the reviewer currently assigned to an Under Review request can complete its review.
Requestor is different

The Requestor capability creates and manages requests. Reviewer eligibility is separately revalidated before assignment and notification.

  1. Choose the narrowest controlRemove a product role for one capability, a team/project assignment for scoped access, or suspend membership for the entire tenant.
  2. Understand active workflow ownershipReassign in-flight reviewer or administrative work before revoking the user where business rules require continuity.
  3. Apply the access changeUse the owning administration surface; do not delete domain audit history.
  4. Allow runtime enforcementThe next heartbeat closes a lease whose membership, module, team, or project access has been revoked.
  5. Verify menus and sessionsReload effective access and inspect active sessions to confirm the expected result.
Role removal is not full removal

A user may still retain another role, tenant membership, or administration access. Review every access dimension before declaring access removed.

Security boundaries

What the model does not assume

These constraints are part of the access design and should remain explicit during future changes.

Menus are not authorization

A hidden route or readonly menu is a presentation control. Every sensitive API must check identity, tenant authority, and resource ownership.

Client organisation IDs are untrusted

Any organisation ID from a route, query, or body must be matched against the authenticated user's active memberships.

Product services are a trust boundary

CreditGuard uses guarded identity introspection for sensitive workflows, but the service must not be directly exposed while all routes lack independent bearer-token enforcement.

Readonly is not universal enforcement

The menu access mode drives supported UI states. It is not a complete backend edit-permission system.

No team means broad eligibility

When an organisation module has no team, all active organisation members are module-eligible. Assign a team when the audience must be restricted.

Seat leases are runtime state

A browser crash may hold a seat until the configured inactivity window expires and the reaper closes the session.

Role and membership are independent

A product role does not identify the tenant. Membership does not automatically grant product workflow capability.

Revocation must preserve audit records

Remove future authority without deleting request, approval, session, or notification evidence required for traceability.

Operational verification

Before reporting access as ready

Validate the effective chain rather than checking only the last assignment changed.

  • User status is active and authentication succeeds.
  • Selected organisation is active and membership is active.
  • Membership level matches the required tenant authority.
  • Organisation module is active and within its intended validity window.
  • The product itself is active.
  • User belongs to the assigned module team, if one exists.
  • Required product role is assigned to the user.
  • Role contains the expected menu grants and access mode.
  • Project allocation and user-project assignment align, if required.
  • A concurrent seat is available for the applicable scope.
  • Backend endpoint authorizes the requested tenant/resource action.
  • Effective access and active sessions show the expected outcome.
